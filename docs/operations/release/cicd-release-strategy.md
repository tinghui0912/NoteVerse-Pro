# CI/CD Release Strategy

This document defines the intended release strategy for NoteVerse on
Kubernetes. It focuses on image tagging, promotion, deployment gates, migration
handling, strict manifest validation, approvals, and rollback decisions.

Related documents:

- `docs/engineering/guides/repository-quality-checks.md`
- `docs/operations/release/container-image-build-strategy.md`
- `docs/operations/deployment/k8s-deployment-runbook.md`

## Goals

- every deployed workload can be traced to an immutable source commit;
- staging and production use the same artifact, promoted by tag/digest;
- production deploys fail before rollout if placeholders, local endpoints, or
  missing Secrets/PVCs remain;
- database migrations are explicit deployment gates;
- rollback decisions account for database, outbox, and object storage
  compatibility.

## Non-Goals

- do not commit production credentials;
- do not put real production hosts into public template overlays;
- do not deploy directly from local developer machines as the normal path;
- do not silently deploy `latest`, `replace-me`, or floating image tags.

## Image Tagging

Container image build details are defined in
`docs/operations/release/container-image-build-strategy.md`.

Build immutable images from a Git commit.

Recommended image tags:

```text
<registry>/noteverse/backend-api:<git-sha>
<registry>/noteverse/backend-beat:<git-sha>
<registry>/noteverse/backend-worker:<git-sha>
<registry>/noteverse/frontend:<git-sha>
```

Optional environment aliases:

```text
<registry>/noteverse/backend-api:staging
<registry>/noteverse/backend-beat:staging
<registry>/noteverse/backend-worker:staging
<registry>/noteverse/frontend:staging
<registry>/noteverse/backend-api:production
<registry>/noteverse/backend-beat:production
<registry>/noteverse/backend-worker:production
<registry>/noteverse/frontend:production
```

Rules:

- deployments should pin immutable tags or digests;
- mutable aliases are allowed only as convenience pointers, not audit source of
  truth;
- production manifests must not contain `replace-me`, `latest`, or
  `example.invalid`.

## Promotion Flow

Recommended promotion path:

```text
commit
  -> quality checks
  -> build backend/frontend images
  -> push images with commit SHA tags
  -> deploy staging private overlay
  -> run staging smoke tests
  -> approve production
  -> deploy production private overlay using the same image tags/digests
  -> run production smoke tests
```

Do not rebuild different production images from the same source after staging.
Promote the tested artifact by immutable tag or digest.

Production should deploy explicit image references. Digest-pinned references are
preferred for staging and required for production once the release package or
GitOps path is the normal deployment route. Development and ad hoc local tests
may use commit SHA tags, but production audit should answer exactly which image
digest is running.

## Private Overlays

Public overlays under `deploy/application/overlays/*` are templates.

Deployable overlays should be private or generated by CI/CD:

```text
deploy/application/overlays/staging-private
deploy/application/overlays/production-private
```

Private overlays must provide:

- real image tags or digests;
- real frontend and API hosts;
- real TLS Secret or cert-manager issuer names;
- existing registry pull Secret name;
- real ConfigMap values;
- existing Secret names;
- existing PVC names;
- GPU node scheduling labels/tolerations.

Before deployment, run:

```bash
python scripts/check_k8s_application_manifests.py \
  deploy/application/overlays/production-private \
  --strict
```

## Deployment Gates

### Pull Request Gate

Required checks:

- backend quality when backend changes;
- frontend quality when frontend changes;
- K8s application manifest guard when application manifests change;
- observability values guard when observability manifests change.

### Staging Gate

Required checks:

- image build succeeds;
- private staging overlay strict validation passes;
- migration job succeeds;
- API health checks pass;
- frontend responds;
- realtime SSE smoke test passes;
- import/review/score/share smoke path passes;
- logs and metrics appear in Grafana.

### Production Gate

Required checks:

- production private overlay strict validation passes;
- staging passed with the same image tags/digests;
- migration reversibility or compatibility is reviewed;
- rollback plan is documented for the release;
- approval is recorded;
- required Secrets/PVCs/TLS assets exist;
- production smoke tests are ready.

## Migration Strategy

Run migrations as a one-shot job before app rollout:

```text
noteverse-db-migrate
```

Rules:

- migration image must match the backend image being deployed;
- failed migrations stop the rollout;
- new API/worker/frontend must not roll out until migration state is known;
- migration logs must be retained in Loki;
- risky migrations require an explicit compatibility note.

Backward-compatible migration examples:

- adding nullable columns;
- adding new tables not read by old code;
- adding indexes concurrently where supported.

Risky migration examples:

- dropping columns;
- changing enum values used by old workers;
- changing outbox states;
- changing object storage key semantics;
- rewriting ownership or quota accounting.

## Rollout Order

Recommended production order:

1. Render and strictly validate private production overlay.
2. Ensure Secrets/PVCs/TLS assets exist.
3. Run migration job.
4. Roll backend API.
5. Roll backend worker.
6. Roll backend beat.
7. Roll frontend.
8. Apply or update Gateway, Certificate, and HTTPRoute resources.
9. Run production smoke tests.

If the API and worker require schema changes, avoid running old workers against
new outbox states unless compatibility is explicitly verified.

## Rollback Decision Tree

### Frontend-only regression

Rollback frontend deployment:

```bash
kubectl -n noteverse-production rollout undo deployment/noteverse-frontend
```

### API regression without migration or storage changes

Rollback API deployment:

```bash
kubectl -n noteverse-production rollout undo deployment/noteverse-backend-api
```

### Worker regression without outbox/schema/storage changes

Rollback worker deployment:

```bash
kubectl -n noteverse-production rollout undo deployment/noteverse-backend-worker
```

### Migration or durable data changed

Do not blindly undo deployments.

First answer:

- can old code read the new schema?
- can old workers process new outbox rows?
- did new code write object storage paths old code cannot understand?
- did quota/accounting state change?
- did migrations drop or rewrite data?

If any answer is uncertain, pause traffic or workers and execute a written
recovery plan.

## Approval Model

Staging:

- automatic deploy is acceptable after quality gates pass;
- manual approval is optional.

Production:

- manual approval required;
- release notes must include:
  - image tags/digests;
  - migration summary;
  - smoke test plan;
  - rollback plan;
  - known risks.

## CI/CD Secrets

CI/CD may need credentials for:

- container registry push;
- cluster deploy;
- private overlay generation;
- external Secret manager access.

Rules:

- store CI/CD credentials in the CI provider's secret store;
- never echo credentials in logs;
- never write credentials into generated artifacts uploaded as public build
  artifacts;
- use short-lived deploy credentials where possible.

## Observability During Release

During rollout, watch:

- API readiness and 5xx rate;
- worker task failures;
- outbox terminal failures;
- realtime SSE errors;
- import/render/playback failure rates;
- storage usage accounting anomalies;
- frontend error reports through the observability facade.

Grafana should link from metrics to Loki logs by service and time range. Trace
integration should wait until OpenTelemetry sampling/redaction is enabled.

## CI/CD Implementation Phases

### Phase 1 - Quality Only

Implemented:

- backend quality workflow;
- frontend quality workflow;
- K8s application manifest guard workflow;
- observability manifest guard workflow.

### Phase 2 - Image Build

Implemented:

- `.github/workflows/backend-api-image.yml`,
  `.github/workflows/backend-beat-image.yml`,
  `.github/workflows/backend-practice-image.yml`, and
  `.github/workflows/frontend-image.yml` build runtime images only for their
  relevant path scopes;
- those workflows push immutable GHCR images on `main` pushes and manual runs;
- `.github/workflows/ml-base-image.yml` publishes the pinned Python/PyTorch CUDA
  base image used by the worker dependency image;
- `.github/workflows/backend-worker-image.yml` is manual-only because the ML
  worker image needs a large CUDA/PyTorch base and should run on controlled
  release infrastructure or a sufficiently provisioned runner;
- images are tagged with the full Git commit SHA and `build-<run-id>`;
- image digests are written to the workflow summary.
- SBOM artifacts are generated for backend and frontend images;
- Trivy blocks images with fixable or already-fixed `CRITICAL`
  vulnerabilities.

Still required:

- feed captured image digests into private staging and production overlays;
- record image digests as release metadata;
- decide when to raise the vulnerability gate to `HIGH,CRITICAL`.

### Phase 3 - Staging Deploy

Partially implemented:

- `.github/workflows/staging-release-package.yml` uses the GitHub `staging`
  Environment variables plus image tags/refs to render and upload a deployable
  staging package;
- when `image_tag` is empty, staging package generation inherits unspecified
  component images from the current staging GitOps `release-metadata.json`;
- the generated package is digest-pinned, includes release metadata, is
  validated in strict mode, and is uploaded as an artifact;
- when `open_gitops_pr=true`, the same workflow promotes the package into
  `deploy/gitops/environments/staging`, validates the GitOps desired state, and
  opens a PR for Argo CD delivery.

The `staging` GitHub Environment must define these non-secret variables before
running `staging-release-package.yml`:

```text
STAGING_FRONTEND_HOST
STAGING_API_HOST
STAGING_TLS_SECRET
STAGING_FRONTEND_BASE_URL
STAGING_BACKEND_CORS_ORIGINS
STAGING_AUTH_COOKIE_SECURE
STAGING_MAIL_DEFAULT_SENDER
STAGING_S3_ENDPOINT_URL
STAGING_S3_REGION
STAGING_S3_BUCKET
STAGING_S3_PUBLIC_BASE_URL
STAGING_S3_FORCE_PATH_STYLE
STAGING_S3_PRESIGN_EXPIRE_SECONDS
```

Credentials such as database URLs, Redis URLs, cookie secrets, S3 access keys,
mail API keys, and Hugging Face tokens are not rendered into this package. They
must already exist in the target cluster as Kubernetes Secrets.

Still required for actual staging deployment:

- runs migration job;
- rolls application workloads;
- runs smoke tests.

### Phase 4 - Production Deploy

Partially implemented:

- `.github/workflows/production-release-package.yml` uses the GitHub
  `production` Environment variables plus image tags/refs to render and upload a
  production release package;
- GitHub Environment approval rules should be enabled for `production` so this
  package cannot be generated without explicit approval.

The `production` GitHub Environment must define these non-secret variables
before running `production-release-package.yml`:

```text
PRODUCTION_FRONTEND_HOST
PRODUCTION_API_HOST
PRODUCTION_TLS_SECRET
PRODUCTION_FRONTEND_BASE_URL
PRODUCTION_BACKEND_CORS_ORIGINS
PRODUCTION_AUTH_COOKIE_SECURE
PRODUCTION_MAIL_DEFAULT_SENDER
PRODUCTION_S3_ENDPOINT_URL
PRODUCTION_S3_REGION
PRODUCTION_S3_BUCKET
PRODUCTION_S3_PUBLIC_BASE_URL
PRODUCTION_S3_FORCE_PATH_STYLE
PRODUCTION_S3_PRESIGN_EXPIRE_SECONDS
```

Still required: add a production deploy workflow that:

- requires manual approval;
- reuses staging-tested image digests;
- validates private production overlay in strict mode;
- runs migration job;
- rolls workloads in order;
- runs production smoke tests;
- records release metadata.

### Phase 5 - GitOps

Planned after the release package path is stable:

- keep GitOps desired state in this repository first;
- add `deploy/gitops/environments/staging` and
  `deploy/gitops/environments/production`;
- use digest-pinned image references and release metadata in desired state;
- install Argo CD in minikube first and sync staging from Git;
- keep production behind Git review and environment approval;
- evolve release package workflows into workflows that open GitOps PRs.

Do not create a separate GitOps repository until deployment ownership,
production access control, or multi-service platform ownership makes that
separation useful. The detailed plan lives in
`docs/operations/release/gitops-evolution-plan.md`.

## Release Metadata

Every production release should record:

- release ID;
- Git commit SHA;
- backend image digest;
- backend beat image digest;
- frontend image digest;
- migration revision before and after;
- approver;
- deployment time;
- smoke test result;
- rollback decision.

This can start as a release note and later move into a database-backed release
audit table.

## Supply Chain Hardening

Future production release hardening should add:

- SBOM generation for every runtime image;
- image signing with Cosign or an equivalent signing tool;
- admission verification for signed production images;
- a policy that rejects unsigned or non-digest production image references.

These should come after digest-pinned staging/production deployment is stable.
Do not block the current GitOps transition on signing infrastructure, but track
it as a production-readiness item.
