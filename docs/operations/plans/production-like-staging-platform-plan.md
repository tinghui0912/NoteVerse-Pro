# Production-like Staging Platform Plan

This plan tracks the next platform migration for NoteVerse.

The local minikube environment is treated as the staging environment and must
exercise the same deployment model intended for production. Differences are
allowed only for external dependencies such as DNS names, managed PostgreSQL,
managed Redis, S3 buckets, mail provider credentials, and cloud provider
implementation details.

## Goals

- use Gateway API and Envoy Gateway as the only documented entrypoint path;
- make minikube a production deployment rehearsal environment, not a shortcut
  development cluster;
- keep staging and production release packages structurally identical;
- use S3-compatible object storage for application files and observability data
  in staging and production;
- keep secrets out of release package artifacts;
- prepare for GitOps without forcing Argo CD into the first migration step.

## Non-goals

- do not keep an alternate Kubernetes entrypoint as a documented fallback;
- do not archive the old entrypoint manifests as an alternate supported path;
- do not render database, Redis, S3 access keys, cookie secrets, mail API keys,
  or Hugging Face tokens into downloadable release artifacts;
- do not introduce Istio, Kong, or Cilium Gateway before NoteVerse has a clear
  need for service mesh, API management, or CNI-level gateway ownership;
- do not use local Docker image loading or a local registry as the normal
  staging rehearsal path.

## Decisions

### D1. Gateway API is the target entrypoint API

Gateway API is the only documented Kubernetes entrypoint model for new
NoteVerse deployments. The application should use:

```text
DNS
  -> LoadBalancer / minikube tunnel / local routed endpoint
  -> Gateway API
  -> Envoy Gateway
  -> HTTPRoute
  -> frontend / backend-api / backend-practice
```

### D2. Minikube equals staging

The minikube deployment path must use the same concepts as production:

- GHCR images;
- registry pull Secret;
- cert-manager;
- DNS-01 certificates;
- Gateway API;
- Envoy Gateway;
- S3-compatible object storage;
- Kubernetes Secrets already present in the cluster;
- release package generated by GitHub Actions or the same renderer script.

### D3. Staging also uses S3-compatible storage

Staging/minikube must not rely on local application storage for uploaded files,
score sources, render assets, playback assets, or observability object stores.

Allowed local state:

- Kubernetes PVCs needed for Prometheus TSDB;
- node-local model cache for model assets;
- temporary work directories that are not durable source-of-truth storage.
- minikube/staging uses `StorageClass/noteverse-local-lvm` for observability
  PVCs through TopoLVM and per-node extra block disks.

### D4. Release packages reference secrets but do not contain secret values

Release package artifacts may contain ConfigMaps and references to Secret
names. They must not contain secret data.

Required secrets are created independently through scripts, External Secrets,
or a future GitOps secret-management layer.

## P0 - Gateway API and Envoy Gateway Migration

Status: completed for repository manifests and release rendering.

Tasks:

- create `deploy/platform/gateway-api/`;
- add Gateway API CRD installation instructions;
- add Envoy Gateway Helm values;
- add environment Gateway, Certificate, and HTTPRoute templates;
- use Gateway API routing resources in the staging overlay;
- use Gateway API routing resources in the production overlay;
- route `/` to `noteverse-frontend`;
- route `/api/v1/*` to `noteverse-backend-api`;
- route practice realtime/WebSocket paths to `noteverse-backend-practice`;
- update `scripts/render_k8s_release_overlay.py` to render host and TLS values
  into Gateway/HTTPRoute resources;
- delete the old entrypoint platform manifests;
- delete or rewrite old entrypoint-specific documentation.

Validation:

- `kubectl kustomize deploy/application/overlays/staging` renders;
- `kubectl kustomize deploy/application/overlays/production` renders;
- `scripts/render_k8s_release_overlay.py` renders `gateway.yaml`;
- strict manifest validation accepts rendered Gateway/HTTPRoute hostnames.

## P1 - Minikube From Zero as Production Rehearsal

Status: in progress.

Completed so far:

- rewrote `docs/operations/runbooks/minikube-from-zero.md` around Gateway API,
  Envoy Gateway, S3-compatible storage, release overlays, and TopoLVM;
- documented Cloudflare DNS records, cert-manager DNS-01 setup, and local
  hosts requirements for the real staging domain;
- documented GHCR pull Secret creation from an explicit token rather than a
  Docker Desktop credential-store file;
- documented application Secret creation without committing secret values;
- documented dedicated application, Loki, and Tempo bucket requirements;
- added `scripts/minikube_app_release_prepare.ps1` as the standard release
  package prepare/apply/wait entry point;
- added `scripts/minikube_smoke_test.ps1`;
- added qemu2/LVM helper scripts:
  - `scripts/minikube_start_lvm_profile.ps1`;
  - `scripts/minikube_start_api_tunnel.ps1`;
  - `scripts/minikube_prepare_lvm_vg.ps1`;
  - `scripts/minikube_install_topolvm.ps1`;
- added `deploy/platform/storage/topolvm/minikube.values.yaml`;
- added `docs/operations/runbooks/local-vm-k8s-lab.md` for the higher-fidelity
  block-device and GPU worker rehearsal path;
- changed `docs/operations/runbooks/minikube-local-k8s-runbook.md` into a
  legacy troubleshooting reference instead of a from-zero entry point.

Remaining tasks:

- perform a clean from-zero deployment using the current runbook;
- verify the rendered release overlay with real GHCR image refs and staging S3
  settings;
- verify Gateway/TLS through the real staging host;
- verify upload, import, review, score detail, derived assets, share, realtime,
  and practice smoke paths;
- decide whether qemu2 minikube is stable enough for routine two-node LVM
  rehearsals on Windows or whether routine two-node storage tests should move
  to the local VM Kubernetes lab.

Current temporary boundary:

- Kubernetes GPU worker validation is paused until a real GPU node is
  available.
- Minikube staging validates frontend, API, practice API, beat, Gateway, TLS,
  S3, and release package flow.
- `backend-worker` can be scaled to zero in minikube and run locally through
  Docker Compose against the same PostgreSQL, Redis, and S3 settings.
- A local VM Kubernetes lab is the recommended next step for validating real
  block devices, TopoLVM, GPU worker scheduling, and model-cache behavior.

Validation:

- a deleted minikube cluster can be recreated from the runbook;
- the deployment uses GHCR images, not `minikube image load`;
- upload, import, review, score, share, SSE, and practice smoke paths pass.

## P2 - Observability Productionization

Status: in progress.

Completed so far:

- added minikube and production Loki values that use S3-compatible storage;
- added minikube and production Tempo values that use S3-compatible storage;
- added minikube Prometheus/Grafana/Alertmanager PVC values backed by
  `StorageClass/noteverse-local-lvm`;
- added production Prometheus retention and PVC sizing values;
- added production OpenTelemetry tail-sampling values for errors, slow
  requests, and baseline successful traffic;
- documented the shared `observability-s3` Secret contract;
- extended the observability manifest guard so staging/production overlays must
  use S3-backed Loki and Tempo storage;
- locally rendered minikube Loki/Tempo Helm manifests and production
  Loki/Tempo/Prometheus/OpenTelemetry manifests;
- added TopoLVM values and scripts for qemu2 minikube profiles with per-node
  LVM volume groups.

Tasks:

- update Loki values so staging and production use S3-compatible storage;
- keep local filesystem Loki only if it is explicitly scoped to a non-staging
  throwaway developer profile;
- set Loki retention:
  - staging: 14 days;
  - production: 30 days;
- document Loki label allowlist:
  - namespace;
  - app/service;
  - container;
  - level;
- explicitly forbid high-cardinality labels such as request ID, user ID, job
  ID, score ID, storage key, email, raw path, or raw error;
- update Prometheus values:
  - staging retention target;
  - production retention target;
  - retention size;
  - PVC sizing notes;
- update Tempo values so staging and production use S3-compatible storage;
- set Tempo retention:
  - staging: 7 days;
  - production: 7 to 14 days;
- add OpenTelemetry sampling policy:
  - low sampling for successful requests;
  - high or full sampling for errors;
  - high or full sampling for slow requests;
- document span/log redaction rules for tokens, passwords, emails, MusicXML,
  OCR text, raw audio, and file hashes;
- ensure dashboards, alert rules, recording rules, and datasource definitions
  are tracked in Git.

Validation:

- observability values guard rejects local endpoints in staging/production
  values;
- Loki and Tempo write to S3-compatible storage in staging;
- Prometheus retention settings are visible in the rendered manifest or Helm
  values;
- test logs can be queried in Grafana after a smoke test.

## P3 - Release Package Hardening

Status: in progress.

Completed so far:

- staging and production release packages now include
  `release-metadata.json`;
- release metadata records environment, commit SHA, image refs, render time,
  workflow run, actor, hosts, and TLS Secret name;
- release package summaries point to the metadata file.

Tasks:

- keep `staging-release-package.yml` and `production-release-package.yml` as
  the current release artifact path;
- add release metadata output:
  - commit SHA;
  - image refs;
  - image digests when provided;
  - environment;
  - render time;
  - operator/workflow run;
- prefer digest-based image refs once image build workflows expose digests in a
  machine-readable way;
- keep production Environment required reviewers enabled in GitHub;
- document when to use per-image override inputs.

Validation:

- release package artifacts contain no Secret values;
- strict manifest validation passes on generated staging and production
  packages;
- generated metadata is enough to answer "what version is deployed?".

## P4 - GitOps Evolution

Status: planned, after P0-P3 are stable.

Tasks:

- introduce Argo CD in minikube after release package deployment is stable;
- add a GitOps staging environment directory or decide on a separate deploy
  repository;
- change GitHub Actions from "downloadable package" to "open a GitOps PR";
- let Argo CD sync staging from Git;
- keep production sync behind approval and Git review;
- evaluate image signing and admission verification after digest deployment is
  stable.

Validation:

- staging desired state lives in Git;
- Argo CD reports healthy/synced state;
- production can reuse the same mechanism with stricter approval gates.

## Execution Order

1. P0: Gateway API and Envoy Gateway migration.
2. P1: minikube from zero runbook and scripts.
3. P2: observability S3 storage, retention, sampling, and label governance.
4. P3: release metadata and digest-oriented package hardening.
5. P4: GitOps with Argo CD.

Do not start P4 before P0 and P1 are verified end to end. GitOps should automate
a deployment model that is already known to work.

Optional node-runtime rehearsal:

- create a local VM Kubernetes lab when LVM and GPU worker behavior need to be
  tested more faithfully than qemu2 minikube can provide;
- keep the application release overlay and Secret contracts identical to
  minikube and production.
